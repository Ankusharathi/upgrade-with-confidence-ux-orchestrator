# Final Demo Script

## Setup

- Target duration: 9–10 minutes
- Main surface: `http://127.0.0.1:8788/#top`
- Upgrade Guide: `http://127.0.0.1:7861`
- Use **Present this project** to move through all 11 chapters.
- Keep the full-screen prototype ready, but begin from the website rather than separate folders.
- Reset the prototype before presenting.

## 0:00–0:40 — Opening

**Show:** Opening chapter and project-state card.

**Say:**

“This is the story of how a six-phase UX Orchestrator took one upgrade question from ambiguity to a design decision that can be inspected and defended.

The customer moment is simple: before I place this order, what exactly changes? The project is synthetic, so the interface is testable while the claims remain carefully bounded.”

## 0:40–1:20 — The trust gap

**Show:** Why the Orchestrator exists.

**Say:**

“AI can produce UX outputs faster than teams can verify them. The risk is losing the reasoning between the request, evidence, design, and approval.

The Orchestrator protects that trail by starting from approved inputs, giving each agent a bounded job, and keeping consequential decisions human.”

## 1:20–2:20 — The six-phase system

**Show:** Phase rail. Select Intake, Discover, Design, Validate, and Deliver.

**Say:**

“Every phase uses the same contract: inputs, agent, skills, artifacts, human gate, and recorded decision.

Notice ‘What changed because of this phase.’ Intake bounds the decision. Discover separates evidence from suspicion. Define chooses one outcome. Design makes it executable. Validate challenges it. Deliver preserves the full trail.”

## 2:20–3:00 — The upgrade question

**Say:**

“A device upgrade is not one price. It can include something due today, a different next bill, a new monthly amount, and conditions that affect credits later.

Public evidence supports that complexity. It does not prove confusion, abandonment, or conversion lift.”

## 3:00–3:40 — The decision trail

**Say:**

“The chain reads in plain language before artifact IDs: what we could verify, the risk we chose to explore, the outcome we designed for, the response we created, and what the prototype could test.”

## 3:40–4:50 — Current, audit, proposed

**Action:** Use all three comparison tabs.

**Say:**

“The current journey supports shopping but distributes the financial consequences. The audit records observable interface gaps, not user-research findings. The proposed experience responds with one persistent Upgrade Impact view before commitment.”

## 4:50–6:20 — Live prototype

**Action:** Open the full-screen six-step prototype.

1. **Eligibility:** “Impact starts as Not calculated because no financial choice has been made.”
2. **Device and payment:** choose the Nova X and monthly payment.
3. **Trade-in:** choose trade-in but omit condition, then continue. Show that the error preserves earlier work.
4. **Impact review:** point to due today, next bill, ongoing effect, trade-in status, credit timing, and plan effect.
5. **Final review:** “Place upgrade order is the only commitment action.”
6. **Unknown result:** if time allows, show that the interface checks status before enabling one safe retry.

## 6:20–7:15 — The prototype pushed back

**Say:**

“The first dry run found two contradictions. Values appeared before their causes, and recovery offered action before order status was known.

The Validate gate returned the project to Design. The failed observations stayed in the record, the prototype changed, and the affected scenarios received a separate retest.”

## 7:15–8:00 — Upgrade Guide

**Action:** Open the floating **Ask Upgrade Guide** launcher from the lower-right corner. Ask one general eligibility question if time allows, then close it to reveal that the case study remains in the same place.

**Say:**

“Upgrade Guide is a separate public-information proof of concept grounded in a verified 150-question Verizon FAQ set. It can explain general upgrade topics. It cannot see an account, order, bill, private eligibility status, or live inventory. When an answer depends on private data, it stops instead of guessing.”

## 8:00–8:40 — Evidence boundary

**Say:**

“This supports claims about orchestration, traceability, prototype behavior, revision, retest, and chatbot boundaries. It does not support claims about real customer usability, conversion lift, production feasibility, accessibility conformance, or live integration.”

## 8:40–9:20 — Close

**Say:**

“The result is not only a redesigned upgrade flow. It is a visible account of how the decision changed.

Reasoning stayed connected. The prototype was allowed to fail. Confidence remained a hypothesis. AI helped create and organize the work, while the designer retained authority over the problem, evidence limits, revisions, and every gate.”

## Short fallback demo

1. Use the staged Current → Audit → Proposed comparison.
2. Show Upgrade Impact in the embedded prototype.
3. Show the two validation before/after pairs.
4. Explain Upgrade Guide’s public-information and account boundaries.
5. Close on Supported / Not Yet Supported.

## Questions to prepare for

### Did conversion improve?

“No conversion measurement was conducted. Conversion improvement is a hypothesis that requires production analytics and real-user research.”

### Did you test with customers?

“No. Validation was an evaluator-led synthetic dry run. It supports prototype workflow coverage only.”

### Is the design accessible?

“Selected keyboard, focus, label, and reflow behaviors were inspected. Specialist and assistive-technology testing remain required, so there is no WCAG conformance claim.”

### Is Upgrade Guide part of the synthetic carrier experience?

“No. It is a separate proof of concept grounded in public Verizon FAQ content. The synthetic Northstar transaction and the assistant have different evidence and system boundaries.”

### Why use an Orchestrator instead of one large prompt?

“The Orchestrator separates responsibilities, preserves versions and evidence, records failed observations, and requires explicit human gates.”
